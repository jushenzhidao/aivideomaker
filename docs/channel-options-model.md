# `X-Channel-Options` 的模型键：**两项目共用的一套语义**

> 状态：**aivideomaker 侧已落地**（2026-09-17）。video-adapter 侧由并行会话同步落地中。
> 本文与 video-adapter 的 `docs/decisions/ADR-012-model-name-passthrough.md` **描述同一套键**；
> 改这里必须同步改那边 —— 两处漂移会让"同一个头、两种含义"，而它决定**计费档位**。
>
> 🔴 **2026-09-17 三次收紧**（每条都有门禁 + 变异自证）：
> ① 通配从"任意模式 + 优先级排序"**降级为唯一一条 `*` 兜底**（§3）；
> ② `model`（渠道钉住）**键整体撤除**，遗留即报错（§9）；
> ③ **兜底＝强制**：`{"*": X}` **覆盖一切**未被精确列出的名字（**含调用方写出的真槽位名**）——
>    它承接了撤除 `model` 后留下的"强制一档"能力。
>
> ⇒ **语义层面已无待裁项**；与 video-adapter 只剩"报错时机"这一处**非语义**差异（§9）。
> 键名、默认透传、未命中 400、值域校验、命中留痕 —— 这几项两边**已完全一致**。

## 1. 键

| 键 | 语义 | 备注 |
| --- | --- | --- |
| `model_map` | 调用方名字 → 上游槽位 的映射表 | **精确键 + 至多一条 `*` 兜底**（见 §3） |
| `upstream_model_map` | `model_map` 的**别名** | 两个都写且内容不同 ⇒ 拒绝（自相矛盾的配置不替配置方挑一个） |
| ~~`model`~~ | 🔴 **已撤除**（2026-09-17） | 曾经的"渠道钉住槽位"。遗留它 ⇒ **渠道配置错误**，不静默忽略（§9） |

**默认 = 上游 model 透传**：一个键都不配时，调用方写的名字**原样当作上游槽位**。
本站（aivideomaker）的"上游槽位"是站点 procedure 名里那一段：`ai.minimaxH3` ⇒ 槽位 `minimaxH3`；
站点把模型编在 **procedure 路径**上，创建请求体里**没有** model 字段。

🔴 **不留任何名字猜测表**。曾经有一张"名字里含 `seedance` 就走 `seedance20`"的正则表，
它把 5 个不同代次的原生 ID 静默压进同一个槽位且**不回告警** ⇒ 真上游实测账单差 **7.3 倍**
（110 vs 15 积分），且落进动态计价槽位后支出上限退化成"事后才知道"。
"哪个名字落哪个槽位"是**控制面知识**，只能由渠道用 `model_map` / `model` 声明。

## 2. 判定顺序（唯一权威表述）

    ⓪ **面级策略** `force_slot`（只有 `/v1/videos` 用） → slot = 面指定的槽位   source=free_only
    ① 映射表**精确**键命中              → slot = 表值                source=model_map
    ② 映射表的 **`*` 兜底**命中          → slot = 表值                source=model_map
    ③ 名字本身是**已知上游槽位**（剥后缀后） → slot = 名字（**逐字透传**）  source=passthrough
    ④ 其余                              → **400**（报文列出已知槽位 + 表里已声明的键 + 怎么改）

- 🔴 **⓪ 是"面的对外契约"，不是渠道可配的东西**（2026-09-20）：`/v1/videos` 承诺"只跑免费线"
  ⇒ 它在 app 层给 `translate_create(force_slot=…)` 传一个固定槽位，**覆盖 ①~④**（连 ④ 的 400
  也一并覆盖：调用方是 OpenAI SDK 用户，拿到失败不如拿到一档免费成片）。
  ⚠️ 它与已撤除的 `X-Channel-Options.model` **不是一回事**：那个是**渠道配置**想钉住槽位
  （会让"配了不生效"难以察觉）；这个是面自己的契约、由代码传入。**覆盖必留痕**：报文如实写出
  "本来会落到哪儿（映射 / 透传 / 本会拒绝）→ 实际落到免费槽位"，证据标 `source=free_only`。
  ⇒ 渠道在这一面上配的映射**不生效**，但绝不静默。**方舟线 `/tasks` 不传这个参数**，①~④ 原样。
- **② 排在 ③ 前面是刻意的**（2026-09-17 用户裁定）：**兜底＝渠道声明"除我明确列出的以外，
  一切名字都落这一档"** ⇒ 它**要**覆盖调用方写出的槽位名 —— 否则运维"这个渠道只跑某一档"的意图
  会落空。这也是 `model` 钉住键撤除后本层**唯一**的"强制一档"手段：**要强制就配兜底**。
  代价是"请求值 ≠ 执行值"，因此每次改写都进 `warnings` 并留 `model_source=model_map` 证据，
  **不静默**；调用方若真要别的模型，运维得把那个名字放进**精确表**（① 优先于 ②）。
- **④ 绝不兜底**（旧的 `return "seedance20"` 兜底就是"写错一个字母就直接付费"的入口）。
  拒绝发生在**任何上游请求之前** ⇒ 不浪费一条带凭据的调用。

## 3. 通配：**唯一一条 `*` 兜底**（2026-09-17 降级）

```jsonc
{"doubao-seedance-2-0-260128": "seedance20",   // 精确键：有几种名字就写几条
 "doubao-seedance-2-5-260628": "seedance25",
 "*": "minimaxH3"}                             // 唯一兜底：其余**一切**名字都落这里（可选）
```

| 规则 | 取值 | 为什么 |
| --- | --- | --- |
| 形态 | **只认字面 `*`**。任何**非 `*` 却含 `*`** 的键（`doubao-seedance-*` / `a*b` / `*pro`）⇒ **渠道配置错误** | 拆掉多模式机制 ⇒ **重叠不可能发生** ⇒"优先级 / 最长匹配 / 歧义报错"这一整类问题消失 |
| 条数 | **至多一条**（"只认 `*`"+ "重复键拒绝"共同保证） | 同一条兜底写两遍没有意义，只会掩盖复制粘贴错误 |
| 匹配 | 兜底对**任何**名字都匹配（含空），**仅次于精确键**：连"调用方写出的真槽位名"也覆盖 | 它是"强制一档"的唯一手段（见 §2 与 §9） |
| 大小写 | 精确键**区分**；同一键的**大小写变体视为重复 ⇒ 拒绝** | 重复键会被 JSON 静默覆盖，而"哪条生效"直接决定账单 |
| 值域 | 必须是已知上游槽位，否则**拒绝** | 否则等于把 400 推到已经带上凭据的上游请求之后 |
| 命中留痕 | 兜底改写了模型值 ⇒ 进 `warnings`（点名 `model_map "*"`）并标 `model_source=model_map` | 静默改模型的账单差异是本项目最贵的一类缺陷 |

> ⚠️ **为什么放弃任意通配**（2026-09-17 决定）：任意模式必然引出"多命中怎么排"的规则，而两个
> 项目在这一点上各写了一套（一个取特异性排序、一个直接报错 —— 对比见
> `docs/channel-options-wildcard-compare.md`）。降级后**这套分歧整体消失**。
> 代价是"覆盖一族名字"必须逐条写精确键；而那些名字是**有限的、已知的**（官方模型 ID 就那几个），
> 所以这不是负担。副作用是 `ADR-012`（"精确匹配，**无通配**"）在这一点上**重新对齐** ——
> 唯一的例外是那条**显式声明的**全通配兜底。

## 4. 拒绝规则（全部发生在任何上游请求之前）

| 情形 | 结果 | `param` 指向 |
| --- | --- | --- |
| 头不是合法 JSON / 不是对象 | 400 | `X-Channel-Options`（渠道配置错误） |
| 表的值不在已知槽位 / 空键空值 / 重复键（含大小写变体） | 400 | `X-Channel-Options` |
| 表里出现**非 `*` 的通配模式**（`doubao-seedance-*` / `a*b`） | 400 | `X-Channel-Options`（报文给出两条出路：逐条写精确键，或保留唯一的 `*` 兜底） |
| **遗留已撤除的 `model` 键**（哪怕取值与解析结果一致） | 400 | `X-Channel-Options`（报文说明它已撤除、该改用 `model_map`） |
| 名字解析不出槽位且没有兜底 | 400 | `model`（**调用方**的错） |
| 头里出现本层不支持的键 | 放行 + **告警**（点名被忽略的键） | — |

把"渠道配置错误"与"调用方传错"分开报：前者是运维的问题，让调用方在 `model` 上找半天会把排查带偏。

## 5. 证据字段（两边各自的落点）

| 项目 | 字段 | 含义 |
| --- | --- | --- |
| aivideomaker | `effective.model` / `effective.model_source` / `effective.model_verified` | 请求值仍是 `requested.model`（**不被改写**）；source ∈ `model_map` / `passthrough` |
| aivideomaker | span `ark.create.submit` 的 `upstream_slot` / `model_source` / `model_verified` | 事后能复盘"这条任务实际跑了哪个模型" |
| aivideomaker | `web_params.procedure` | 真正打到站点的 procedure（`ai.<槽位>`） |
| video-adapter | `effective.model_map_applied` / `effective.model_requested` | 同上语义（响应体已不含 `model`，这一对是判据） |

解析结论**每次都进 `warnings`**（命中精确键、命中兜底、槽位未实测）——
静默改模型的账单差异是本项目定义为最贵的一类缺陷。

## 6. 唯一登记在案的差异：槽位值域的"掌握程度"

两边都用"**该层已知的上游槽位清单**"作为值域，但掌握程度不同：

| 项目 | 值域来源 | 对"未实测槽位"的处理 |
| --- | --- | --- |
| video-adapter | 上游（aivideomaker）的槽位清单**已实测** | 表外名字 ⇒ 400 |
| aivideomaker | 站点 11 个模型键（i18n 文案，**已知**）∪ 已实测 procedure 的槽位 | **允许**配置，但标注 `model_verified=false` + 告警 |

aivideomaker 侧之所以"允许但不静默"：站点 11 个模型的 procedure 名**尚未取得**
（现有抓包只是路由级 chunk；`docs/web-reverse/README.md` 的待办）。禁止配置会让映射表在
清单到手之前完全无法配置；而不标注就等于把"推断"当"事实"。⇒ 取"允许 + 留痕"。

### 未验证的那一步（必须知道）

`channel_options.procedure_for_slot()` 现状是 `ai.<槽位>` **按命名形态推断** ——
全站点只实测出 `ai.minimaxH3` 一条生成 procedure。⇒ 映射到非 `minimaxH3` 槽位后，
若 procedure 名不对，表现为**上游 NOT_FOUND**（显式失败、不建任务、不计费）。
拿到清单后：把推断换成**表**，并让表里没有的槽位直接被拒。

## 7. 迁移（旧的"忽略模型名"行为）

本层旧行为是**写死 `ai.minimaxH3`**、任意模型名都通过。要恢复它：

```jsonc
// 兜底表（**唯一**手段，也是本层唯一的"强制一档"）：其余一切名字都落这一档
{"model_map": {"*": "minimaxH3"}}
```

⚠️ **不要再用** `{"model": "minimaxH3"}` —— 该键已于 2026-09-17 **撤除**，遗留即报错（§9）。
它就是这一版之前文档里的"① 钉住（推荐）"，现在**会 400**。

**注意**：上面的兜底**会覆盖**调用方写出的真槽位名（② 优先于 ③）—— 这正是"只跑一档"要的效果：
调用方写 `seedance20` 也跑 `minimaxH3`。代价（请求值 ≠ 执行值）由**留痕**兜住：
每次改写进 `warnings`、证据标 `model_source=model_map`。
若某个名字**必须**走别的槽位，把它写进**精确表**（① 优先于 ②）。

## 10. 落点评估：映射表该不该放在 `X-Channel-Options.model_map`

**结论：在当前形态下应当放在这里** —— 这不是偏好，是结构性结论；但它附带三条约束与一个搬家触发条件。

### 为什么是（结构性理由，不是"图省事"）

1. **本服务的主形态是 `AVM_AUTH=passthrough`**（调用方自带网页会话 cookie、多租户共用同一个进程）
   ⇒ "一个渠道一套映射"**只能逐请求带进来**：部署级 env / 挂载文件**无法区分租户/渠道**。
2. **本层不持有模型知识**（"知识归控制面、数据面只执行"）⇒ 配置必须外置；
   `X-Channel-Options` 已经是"渠道知识"的落点（`provider` / `credit_table` / …），复用而不新开头。
3. **规模不构成理由**：实际用量是"渠道声明的几条到几十条"（约 **1~3KB**），而原始 socket 实测
   **20KB / 70KB / 120KB / 293KB 的请求头全部进到应用层**（`video-adapter/docs/03_引擎架构.md`
   的 gunicorn 段）⇒ "头会爆"这条不成立；也不必再去调 `limit_request_field_size`。
4. **改配置零部署**：不动 env / compose、不重启，与"渠道级声明"的运维形态一致。

### 必须配的三条（都是当晚踩出来的）

**A. 入口唯一 —— 不做两层配置。** 不要引入"部署级默认 + 请求头覆盖"。
透传形态 + 两层配置 ⇒ 必然出现"这次到底谁的取值生效"的歧义（同类教训已有：多个项目共用同名
凭据变量时谁优先）。要么全在头里，要么全在文件里，**不要并存**。

**B. 可审计 —— 表是每请求携带的。** 本层因此**没有"当前生效配置"的快照**。
除现有的 `model_source`（本仓库）与 `model_map_pattern`（video-adapter），建议再挂一个
**表指纹**（`sha256(规范化表)[:12]`）到 span 与内部视图：出问题时能判定"这次用的是哪一版配置"，
而**不把整表塞进 trace**（控体积）。注意别用 JSON 原文算指纹 —— 键序会变，要先排序规范化。

**C. 写死规模边界与搬家触发。** ≤ 几十条（~1~3KB）留在头里；**要到上百条时不要撑大头**，
改为**部署级文件 + 头里放引用**（如 `{"model_map_ref": "aivideomaker-prod"}`）——
保留"逐渠道选择哪一套表"的能力，同时把大表移出请求路径。这条触发条件必须写死在文档里，
否则它会悄悄长到几百条。

### 两个边界（可能反转结论）

- **计费档位由入参决定**：头归调用方控制 ⇒ 调用方（或其被攻破的前端）能改自己的落点。
  若调用方只可能是你自己的控制面（new-api / BFF）且在内网，这是可接受的；**Ark 面要对外时，
  应当在部署层限制或剥离外部传入的同名头**（只接受受信来源）。
  ⚠️ 代码里**没有**强制这一点，只有告警与证据 —— 这是刻意的（不替部署层做信任决策），
  但必须知道它不在代码的防线内。
- **更根本的取舍：谁来翻译。** 若接入面允许调用方**直接写上游槽位名**，本层**根本不需要映射表**
  （更严格、零知识）—— `model_map` 存在的唯一理由是"**调用方写的是它自己的模型名**"
  （例如火山官方 ID），而不是本站槽位名。这条同时解释了 §9 的 D3：video-adapter 撤掉钉住键，
  正因为它已经在**上一层**完成了翻译 —— 而 2026-09-17 本层也**按同一理由撤除**了该键
  （结论：翻译与强制都在上层，本层只执行）。⇒ 先问"我这层的调用方写的是什么"，再决定要不要配表。

### 当前的可行域（比落点更重要）

**从"调用方写的名字"到"请求真正打到哪个端点"，中间是两段跳，不是一段：**

    调用方名字 ──① model_map 映射表──▶ 槽位 ──② procedure 名──▶ POST /api/<procedure>

- **① 是配置，你说了算**：表由你写、值受白名单校验（必须是已知槽位）、命中留痕且可查。
- **② 是代码里的推断，没有任何地方能配**：`channel_options.procedure_for_slot()` 现在返回
  `f"ai.{槽位}"` —— 照"同一命名形态"猜。全站**只实测出 `ai.minimaxH3` 一条**生成 procedure，
  站点完全可能给别的槽位起另外的名字（`ai.seedance_2_0`、`ai.video.…`）或走另一套参数形态。

⇒ **"配了映射"只保证第一段。** 例：配 `{"doubao-seedance-2-0-260128": "seedance20"}`
只意味着"这个名字会变成槽位 `seedance20`"；紧接着发出的 **`ai.seedance20` 是猜的** ——
猜错的表现是上游 **NOT_FOUND**（该站对不存在的 procedure 就是这个回应；`TESTCASES.md` §10 把
20 个 procedure 名探了一遍、全部 NOT_FOUND，是同一现象）。它**响亮**：不建任务、不计费、不静默；
但你在**配置那一刻**看不出来，要等第一条真实请求回来才知道。

⇒ **实操建议：在 procedure 清单到手之前，只配"单档形态"**
（`{"*": "minimaxH3"}`），**不要急着铺多槽位映射** ——
它不会"更早生效"，只会把请求送上推断出来的 procedure 名。

## 11. 与 `X-Script` 脚本替换的关系（谁说了算）

**结论：这不是"优先级竞争"，而是"脚本是执行器"。** `X-Script-Ref` 决定**用哪段翻译逻辑**，
`model_map` 只是**喂给它的数据** ⇒ 真实关系是 **`X-Script-Ref` ≫ `model_map`**，
而且这个"高优先级"**当前没有护栏**：脚本不读 `model_map`，映射就**静默失效**。

### 事实（video-adapter 现状，读码取证）

| 事实 | 证据 |
| --- | --- |
| 脚本来源只有 `X-Script-Ref`（`X-Script` / `X-Script-64` 本部署**拒绝**） | `adapter/api.py:64-66` |
| 只能选 store 里的脚本：manifest 登记 + 摘要锁定 + 沙箱装载 | `adapter/scriptstore.py`（`resolve` / `load`） |
| 引擎**不读** `model_map`，只把它原样放进 `ctx.options` | `adapter/tasks.py:170` `options=dict(channel.options)` |
| `model_map` 由**脚本**消费 | `script_store/aivideomaker/video@v1.py:284` `resolve_model_map(options, …)` |
| manifest **不声明**脚本消费哪些键 | `script_store/manifest.json`（只有 scripts / digests） |

### ⚠️ 同一头里有**两种权威**（这是真正的坑）

| 键 | 谁强制 | 换脚本会怎样 |
| --- | --- | --- |
| `provider` | **引擎**（`adapter/channel.py:110`） | 不受影响 |
| `max_concurrency` | **引擎**（`adapter/channel.py:40`） | 不受影响 |
| `rehost` | **引擎**（`adapter/tasks.py:254`） | 不受影响 |
| `model_map` / `upstream_model_map` | **脚本** | **静默失效** |
| `max_credits` / `credit_table` / `allow_unpriced` | **脚本** | **支出上限静默消失**（ADR-004 的"本地强制"整个在脚本里，引擎零引用） |

⇒ 运维**从键名看不出**这个键到底会不会生效。后两行是同一个洞：
**换一次脚本版本（`@v1` → `@v2`）或换一个 vendor 的脚本，就可能悄悄换掉模型落点与花钱上限。**

### aivideomaker 侧的对照（反而更稳）

本仓库**没有脚本机制**：模型解析在引擎里（`translate_create` → `channel_options.resolve_model`），
**调用方无法通过"选一个执行器"来绕过或改写它** —— 换执行器只有一条路：部署新版本。
这是引擎级实现被低估的优点，代价是**脚本不能再对名字做自己的定制**（要改就得改本层代码）。

### 建议（按性价比排序）

1. **声明式契约**：`manifest.json` 给每个脚本声明它消费的 `options` 键
   （如 `"options": ["model_map", "max_credits", "rehost"]`）；引擎在"配置里出现脚本未声明的键"时
   **告警**（未声明的键 = 配了也不生效）。这与本仓库对未知键的告警同形，且正好覆盖"换脚本"这条触发路径。
2. **选脚本时校验**：`X-Script-Ref` 指向的脚本不消费 `model_map`（或 `max_credits`），
   而同一渠道的头里又配了它 ⇒ **响亮失败**（"执行器与配置不匹配"），别静默放行。
3. **门禁**：对声明消费某键的脚本，契约测试必须断言它**真的读** ——
   喂一张表 ⇒ 断言 `effective.model_map_applied is True`；给一个上限 ⇒ 断言超限被拒。
   否则 manifest 只是一句声明（"实现了 ≠ 接线了"的脚本版）。
4. **文档**：video-adapter 自己文档的键表要加一列**权威层级**（引擎强制 / 脚本消费）。
   两边的证据字段（`model_map_applied` / `model_map_pattern` ↔ `model_source` / `model_verified`）
   也应互相可映射，别让"哪一层做的解析"变成需要读代码才能回答的问题。
